# supabase

The Postgres database behind Element (Supabase free tier). The SQL files here are the only source of truth for the schema. The ingest script (`ingest/`) writes through service-role RPCs. It runs on a laptop today; the cloud version (Edge Functions `brief-summary` and `ingest-source`, scheduled by pg_cron) is in `functions/` (see `functions/functions.md`), written but not deployed.
**Cloud cutover:** the apply order for the pending migrations, secrets, deploy commands, the 24-hour comparison, rollback and laptop shutdown are in [`CUTOVER.md`](CUTOVER.md). Apply `20261110000000_watchdog.sql` (3-argument `api.ai_usage_take`) before redeploying the functions.


## Schemas

| Schema | Exposed? | What is in it |
|---|---|---|
| `ingest` | no | raw collected items (`ingest.items`) |
| `core` | no | published cards and their sources, macro numbers, ranking settings, app config, categories, user prefs and events; `core.story_links` stores update/angle/related pairs (RLS enabled, no client policies) |
| `api` | **yes, the only one** | views and functions the app and the ingest script call |

Row-level security is on for every table. The app never reads `core` or `ingest` directly; everything goes through `api`.

### Offline evaluations (`tests/eval/`, not pass/fail)

Measure search and feed quality on the real SQL in PGlite; nothing is written to disk or the network.

- `node supabase/tests/eval/search-eval.mjs [--scale N] [--snapshot cards.json] [--skip <migration>] [--ablate] [-v]`: a 39-query battery (tickers, company names, typos, topics, multi-word) with a hand-written relevance pattern per query; prints precision at 5 / 10 per query class, timings and a paging check (guest and signed in). `--skip search_v6` measures the version before; `--ablate` re-runs with each v6 setting off.
- `node supabase/tests/eval/feed-eval.mjs [--scale N] [--sessions 4] [--v3]`: guest Trending / Latest full scrolls (repeats, skips, macro share of the top 10 / 50, micro and non-economic Federal Register cards per 10, longest topic run, age), with the Federal Register switch off and on; five synthetic readers (rates watcher, big-tech investor, bank investor, skimmer, new reader) over several For you visits (precision of the top 10, topics, novelty, macro share), a full For you scroll, Following and first-page timings. `--v3` adds the v3 ranker for comparison (it stays off in production).
- `node supabase/tests/eval/scale-bench.mjs [--scale 10] [--runs 3] [--events N] [--trgm]`: loads the synthetic corpus at N x (bulk insert) and one signed-in reader with N events, times the read RPCs (Trending, Latest, For you v5 and v3, Following, company RPCs, the search battery) before the `20261121*` migrations, applies them on the same data, times again, and reports whether each result is unchanged plus the battery's precision at 5 / 10 before and after. The battery itself is in `battery.mjs`.
- `corpus.mjs`: deterministic synthetic corpus shaped like the live feed (about 290 cards per scale unit); `--snapshot` takes cards in the api shape instead (keep such files out of git). `db.mjs`: the shared PGlite setup.

## Capacity assumptions: For you path (M9b scale review, 2026-11-10)

Checked by `tests/foryou_m9b_scale_check.sql` in PGlite (WebAssembly, one thread; Supabase Postgres is several times faster). Last run (2026-11-11, 100,000 cards, 24,400 in the window, 20,000 readers x 10 events + one reader with 300): For you v5 page 1 942 ms, again 780 ms; 0 sequential scans of core.user_events and core.blurbs; v3 path forced past the guard 13.1 s (core.v3_scores 11.5 s over 2,300 scored cards; the check loads cards with triggers off, so core.card_features is empty and every v3 feature is computed per request: an upper bound, prod precomputes them at publish); api.related_cards 105 ms; core.refresh_trending 11.1 s (cron batch). At 10,000 cards: v5 page 1 1.3 s, v3 1.7 s.

- **Cards.** For you reads the cards in `for_you_window_days` (30) through `blurbs (sort_at desc, id desc) where published`, computes the reader-independent score of each and keeps the best `foryou_max_scored` (1500) plus room for the reader's seen cards (at most `seen_exclude_max`, 800). This cut is the only step that grows with the window (a sort of the window's rows, no join to events). Everything after it is bounded by about 2,400 cards: taste, explore, crowd, collab, company tags (`card_companies` primary key per candidate), seen penalty and the v3 features. Extras past the cut are bounded too: live data cards (one per series, a few dozen, `blurbs_data_live_idx`), key-series cards (12 series) and at most `fy_follow_company_max` (50) followed-company cards (`card_companies_ticker_sort`).
- **Events.** Every per-request read of `core.user_events` is one reader's events in a time window (`user_events_user_time_idx`; `user_events_user_blurb_idx` for the dislike anti-join; `user_events_view_idx` for the seen list). No request scans all events. A reader's events are bounded by the tracking caps (720 a day) and by `ml_purge_events_days` (60).
- **Per page after ranking.** `core.fy_post` touches at most 30 cards: their company tags, the reader's reactions on cards with those tickers, one `core.user_taste` call and the reader's topic list. The micro gate calls the base at most `micro_gate_max_calls` (4) times per page.
- **v3 cost guard.** `api.feed_for_you` serves v3 only while the window holds at most `v3_max_candidates` (3000) cards; above that it serves v5 (with the same M9b terms). With about 25,000 cards in the window For you is v5 unless the guard is raised; the scale check forces v3 once to measure it.
- **Batch jobs.** `core.refresh_trending` (cron) reads the events of the last `trend_window_hours` (48) through `user_events_time_idx`, and the co-engagement pairs of `collab_window_days` (14) with at most `collab_max_per_user` (50) cards per reader, so its work grows with readers x 50^2 in the worst case. At 20,000 active readers it is the first job to watch: give it a longer interval before raising those caps.
- **Related cards.** `api.related_cards` reads story links, then cards sharing a ticker or a company tag (`card_companies_ticker_blurb`); no events.
- **When to act.** Window above about 50,000 cards: lower `for_you_window_days`, or store the reader-independent score in an indexed column so the cut becomes an index range scan. Above about 100,000 daily readers: run `refresh_trending` less often and cap collab pairs per card.

## Setting up a new project (paste order)

1. Create a Supabase project. In **Project Settings → Data API → Exposed schemas**, set `api` only.
2. In the SQL editor, paste and run each migration in the order above. Each should report "Success. No rows returned".
3. Run `tests/ranking_check.sql` (part 1, then part 2).
4. Create the two test users, run `tests/accounts_check.sql`, `tests/account_delete_check.sql`, `tests/signals_check.sql`, `tests/trending_check.sql` and `tests/collab_check.sql` and `tests/web_column_check.sql` (no test users needed), then delete the test users.
5. Set the dashboard-only settings below.
